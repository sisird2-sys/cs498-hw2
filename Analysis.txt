Discussion

The main finding is that the europe-west1 VM was much slower than the us-central1 VM. /register went from about 140 ms to 444 ms. /list went from about 44 ms to 330 ms. There are two reasons for this. First, the scripts ran from Cloud Shell, which is in a Google data center in the US. Every request to the europe VM has to cross the Atlantic and come back. Second, the Firestore database is in us-central1. When the europe VM gets a request it has to make another trip back to the US to read or write the data. This means each europe request crosses the ocean about twice. The us-central1 VM is in the same region as the database, so that extra trip is very short. /register was slower than /list on both VMs because a write has to be saved before the server can reply. The us-central1 /register times also jumped around a lot, from 22 ms to 482 ms. The slow ones were likely the first connections warming up or short delays on the database side.

The consistency test found the new username every time. It was missing 0 out of 100 times. This does not show the replication lag the assignment talks about. Firestore in Datastore mode is strongly consistent for reads and queries. Both VMs also use the same single database in us-central1 and not separate copies. The europe VM only sends its /list request after the us-central1 /register has already returned. By then the write is saved, so the read sees it. However, lag would show up in a system where each region has its own copy of the data that updates in the background. In that case a read right after a write in another region could miss the new data for a short time. The extra latency on the europe VM is the cost of always reading up to date data from one central database.
